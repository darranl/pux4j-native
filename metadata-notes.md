# reachability-metadata.json — notes

`src/main/resources/META-INF/native-image/reachability-metadata.json` is the GraalVM
reflection/resource/JNI configuration for every native image this repo builds. It is **one
file shared across all app profiles × target profiles** (`smoke` / `validation` / `demo` /
`dice-demo` / `smoke-emulator` / `validation-emulator` × `hat-2in9v2` / `hat-2in13v4` /
`x86_64` / `aarch64`) — there is no per-profile split. This has one hard consequence:

**Entries must only ever be added, never wholesale-replaced.** Any tool or process that
regenerates this file from a single app's tracing run and writes over the whole thing will
silently strip out everything every *other* profile's native build depends on. See the
`MergeMetadata.java` gotcha below — this already nearly happened once.

`augment/reachability-metadata.json` is a separate, hand-curated file (currently resource
globs only — e.g. the validation test's PNG icons) that native-image picks up independently.
It is not affected by anything below.

## If this file were deleted

**It could not be regenerated by a single script run.** Reconstructing it requires:

1. Re-running the tracing agent against several different apps/profiles (demo, dice-demo,
   smoke-emulator, validation-emulator — see "Recreation procedure" below for how), **plus**
2. Manually re-deriving the hand-authored aarch64 hardware entries (Pisces SW renderer, JNI
   `ThrowNew` exception classes, SSE effect peers) that came from iterative crash/fix cycles
   on real Pi hardware in May 2026 — no tracing run on x86_64 reproduces these, because the
   aarch64 SW rendering path is never exercised on x86_64 (which uses ES2/GPU instead), **plus**
3. Re-registering the ~212 ES2 shader loader classes for the dice demo (currently brute-forced
   in via a one-off extraction script, not tracked as a repeatable process — see W2 in
   `notes/project-plan.md`'s Technical Debt table).

In short: full reconstruction from scratch is a multi-session effort involving real hardware,
not a `mvn generate-metadata` command. This document is the closest thing to a recreation
procedure that exists, but treat the committed file as the source of truth — don't delete it
expecting to get it back easily.

## History — how each part got here

### Base entries — `pux4j-demo`, via the tracing agent

`scripts/generate-metadata.sh` runs the JVM `pux4j-demo` build under
`-agentlib:native-image-agent=...`, exercising increment/decrement/mouse-move/right-click, then
converts the agent's output via `scripts/MergeMetadata.java`. This produced the bulk of the
base JavaFX reflection entries (Glass, Prism, font handling, etc.).

### Dice demo additions — ES2 shaders and the Circle entry (2026-05-22)

Building `pux4j-dice-demo`'s native image surfaced two more workarounds, tracked as tech debt:

- **W7** — `javafx.scene.shape.Circle` was hand-added directly to this file (a bare
  `{"type": "javafx.scene.shape.Circle"}` entry) because the tracing agent was never re-run
  after `DieView` started using `Circle`. Still outstanding — see `notes/project-plan.md`.
- **W2** — the dice demo's styled layout (`HBox`/`VBox`, CSS backgrounds/borders) triggers ES2
  shader loading via `Class.forName("com.sun.prism.shader.Xxx_Loader")` for shaders the tracing
  agent's simpler counter-demo run never exercised. All 212 `*_Loader` classes and 227 `.frag`
  resource files were brute-force registered by extracting the full list from
  `javafx-graphics-23.0.1-linux.jar` directly, rather than captured organically. See diary.md
  2026-05-22 for the full account, including why `DieView` uses `Pane`+`Rectangle` instead of
  `Canvas` to avoid needing the Canvas-specific shaders in this set (W1).

### aarch64 hardware entries — Pisces SW renderer, JNI, SSE peers (2026-05-21)

The tracing agent only ever runs on x86_64, where JavaFX uses the ES2/GPU rendering path. On
aarch64 (the actual Pi hardware), JavaFX falls back to the Pisces **software** renderer, which
is a completely different code path with its own JNI/reflection needs that no x86_64 trace can
capture. These were found by an iterative crash-log-fix cycle running the native binary
directly on `diamondpi` (Pi 500+):

- 5 JDK exception classes (`ArrayIndexOutOfBoundsException`, `IllegalArgumentException`,
  `IllegalStateException`, `NullPointerException`, `OutOfMemoryError`) with `jniAccessible: true`
  and `<init>(String)` registered — needed for Pisces' native C code to call `JNI_ThrowNew`
  without triggering a masking `FatalError`.
- Pisces field registrations (`AbstractSurface.nativePtr`, `JavaSurface.dataInt`,
  `PiscesRenderer.nativePtr`/`surface`, `Transform6`'s six int fields) — needed for
  `GetFieldID` calls in the native Pisces renderer.
- Effects renderer classes (`PSWRenderer.createRenderer`, `JSWRendererDelegate.<init>`) and all
  4 SSE effect peer classes (`SSEBoxBlurPeer`, `SSEBoxShadowPeer`, `SSELinearConvolvePeer`,
  `SSELinearConvolveShadowPeer`) — needed for DropShadow/effects to render on aarch64's
  NEON-backed SSE path.

Full technical detail, including exact native source references in the OpenJFX checkout, is in
`diary.md` under `## 2026-05-21`.

### PNG icon resources — kept in `augment/`, not here (2026-05-29)

The validation test's PNG icons are registered as unqualified `glob` resource entries in
`augment/reachability-metadata.json` (no `"module"` field — the native builds that need them
use classpath mode, where module-qualified entries don't match). See diary.md 2026-05-29.

### Emulator additions — Canvas + Logback + Pi4J/PNG fallback (2026-08-30)

See "Recreation procedure" below — this is the process used tonight to add
`smoke-emulator`/`validation-emulator` native image support, and the template for adding
any future app/profile.

## The GraalVM version gotcha (found 2026-08-30) — read this before running `generate-metadata.sh`

**`scripts/generate-metadata.sh` / `scripts/MergeMetadata.java` are currently broken against
the GraalVM version this project uses (GraalVM CE 25.0.2).**

`MergeMetadata.java` was written to read the *legacy* split agent output format:
`reflect-config.json`, `resource-config.json`, `jni-config.json`. GraalVM CE 25.0.2's
`native-image-agent` no longer writes those files by default — it writes directly in the
**new unified `reachability-metadata.json` schema** (top-level keys `reflection`, `resources`,
`foreign`) into the `config-output-dir`.

The result: running `MergeMetadata.java` against a fresh trace from this GraalVM version reads
three files that don't exist, finds empty arrays for all of them, and happily writes out
`"Written: ...   reflection entries : 0   resource entries : 0   bundle entries : 0   jni
entries : 0"` — **it looks like success.** If `generate-metadata.sh` were run end-to-end today
as documented, it would silently overwrite the real `reachability-metadata.json` with an
effectively empty file, destroying every entry described above.

**Do not run `scripts/generate-metadata.sh` until this is fixed.** `MergeMetadata.java` needs
updating to detect and pass through the new unified format (or simply be skipped, since the
agent already writes the exact file format we want — see the procedure below, which bypasses
it entirely). Tracked as **W12** in `notes/project-plan.md`'s Technical Debt table.

A second, unrelated bug in `MergeMetadata.java` (line ~130: `cfg.getJsonArray("bundles",
JsonValue.EMPTY_JSON_ARRAY)` — `JsonObject.getJsonArray` has no such 2-argument overload in
`jakarta.json-api` 2.1.3, confirmed via `javap` against the actual jar) was also found and
fixed tonight (changed to `(JsonArray) cfg.getOrDefault("bundles", JsonValue.EMPTY_JSON_ARRAY)`,
using the `Map` interface `JsonObject` extends). That fix was necessary just to get the tool to
compile at all, and is independent of the format gotcha above.

## Recreation procedure — adding coverage for a new app/profile

This is what was actually done tonight to fix `smoke-emulator`/`validation-emulator`'s
`ClassNotFoundException: javafx.scene.canvas.Canvas` at native-image runtime. Use it as the
template for any future app/profile that needs new metadata coverage. All commands below run
from `pux4j-native/`.

1. **GraalVM CE active, `pux4j-ui` installed:**
   ```
   sdk use java 25.0.2-graalce
   cd ../pux4j-ui && mvn install -DskipTests && cd -
   ```

2. **Populate `target/deps-<suffix>`** for the profile being traced (this is the exact
   module-path dependency set the native build itself will use):
   ```
   mvn -P smoke-emulator,x86_64 -DskipTests prepare-package
   ```

3. **Run the app directly under the tracing agent**, writing to a **scratch** directory (not
   `generate-metadata.sh` — see the gotcha above):
   ```
   mkdir -p target/generated-metadata-emulator
   java --module-path target/deps-x86_64 --add-modules dev.pux4j.ui.emulator \
     --enable-native-access=javafx.graphics \
     -agentlib:native-image-agent=config-output-dir=target/generated-metadata-emulator \
     -Dpux4j.emulator.display=ssd1675a -Dpux4j.emulator.scale=3 \
     -m dev.pux4j.ui.validation/dev.pux4j.ui.validation.DisplaySmokeTest
   ```
   Exercise the app fully, then let it exit **normally**. The agent only flushes its config on
   clean JVM exit — a force-killed or forcibly-closed window produces an empty or missing
   config file, which looks like "nothing was captured" and is easy to misdiagnose as the tool
   being broken again.

4. **Repeat for other entry points that exercise different code paths**, using
   `config-merge-dir=` instead of `config-output-dir=` to accumulate into the *same* scratch
   directory rather than overwrite it:
   ```
   java --module-path target/deps-x86_64 --add-modules dev.pux4j.ui.emulator \
     --enable-native-access=javafx.graphics \
     -agentlib:native-image-agent=config-merge-dir=target/generated-metadata-emulator \
     -Dpux4j.emulator.display=ssd1675a -Dpux4j.emulator.scale=3 \
     -m dev.pux4j.ui.validation/dev.pux4j.ui.validation.HardwareValidationTest \
     --touch-native-width 296 --touch-native-height 128
   ```
   (This second run covers touch/mouse handling that the smoke test alone doesn't exercise.)

5. The scratch directory's `reachability-metadata.json` is now **already** in the consolidated
   format this project wants — no `MergeMetadata.java` conversion step needed, given the
   gotcha above.

6. **Diff by `type` against the real committed file** with `jq` — never just copy the scratch
   file over the real one:
   ```
   jq -r '.reflection[].type' target/generated-metadata-emulator/reachability-metadata.json | sort -u > /tmp/new-types.txt
   jq -r '.reflection[].type' src/main/resources/META-INF/native-image/reachability-metadata.json | sort -u > /tmp/old-types.txt
   comm -23 /tmp/new-types.txt /tmp/old-types.txt
   ```
   (equivalently, `jq` with `select(.type as $t | $existing_types | index($t) == null)`).

7. **Review each genuinely-new entry** — confirm it makes sense for what the app actually does
   before adding it. Don't add anything that looks spurious.

8. **Manually append** the new entries into the real file's `reflection` array (never overwrite
   the whole file). Commit with a message describing what app/profile was traced and why.

### What this captured tonight

22 new reflection entries, all additive:

- `javafx.scene.canvas.Canvas` — the actual fix for the `ClassNotFoundException` that started
  this investigation. `EInkEmulatorWindow` is the first code in this project to use `Canvas`
  directly in a way that reached native-image runtime (the dice demo deliberately avoids it —
  see W1 above).
- ~11 Logback classes (`PatternLayoutEncoder`, `ConsoleAppender`, `DateConverter` and other
  pattern converters, `DefaultJoranConfigurator`, etc.) — needed for Logback's Joran XML config
  parser to build the logging pipeline reflectively at startup. Apparently never fully
  exercised by previous traced apps.
- `com.pi4j.plugin.ffm.FFMPlugin`, `dev.pux4j.ui.core.internal.PngDisplayDriverFactory` — Pi4J's
  plugin loading and the PNG-driver fallback path, both exercised because this ran off-Pi.
- `com.sun.org.apache.xerces.internal.jaxp.SAXParserFactoryImpl`,
  `sun.text.resources.cldr.FormatData`/`FormatData_en` — JDK internals used by Joran's XML
  parsing and locale-aware formatting.
